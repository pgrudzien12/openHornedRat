# Ranged combat behavioural handoff (#147, #101, #112)

Scope: player Fire orders, scripted shooting, ordinary missiles, artillery, projectile flight and impacts, and relevant deaths. Distances are battlefield units (24 per inch), angles are 512 units per turn, and one battle tick is 100 ms. Treat ammunition as unlimited for the immediate engine work. This is a static research handoff; tick examples below are deterministic acceptance fixtures, not claims of a recorded play session. Spellcasting is outside scope, except that some innate attacks use the spell projectile pool and impact rules.

**Ammunition finding:** the inspected ordinary Fire order, readiness, volley and missile launch paths contain no stock-of-ammunition check or decrement, and the documented unit stat format has a weapon code but no ammunition field. This supports effectively unlimited ordinary Fire in this scope. It does not exclude a mission-specific script limit elsewhere; none is established here. Do not invent an ammo counter.

## 1. Fire order and target state

Only player owned selected units can receive a player order. Fire is offered by the attack panel for Archers and Artillery; scripts can initiate the same shooting behaviours for other eligible units. A unit charging, fighting in melee, broken, pursuing or braced refuses a new Fire order. An order to a unit with no usable missile weapon cannot start a shot. The click is resolved in the 3D view or minimap with the same battlefield picking rule. Once an accepted ordinary Fire event is queued, an already moving shooter halts. A refused order has no new shooting target or volley; no dedicated refusal text for the general busy or weaponless cases was found.

| Click under Fire cursor | Accepted ordinary shooter state and next action | Player feedback |
|---|---|---|
| Other unit, including enemy, friendly or neutral | Retain that unit as the target. Enter repeated targeted shooting; a fresh volley is attempted whenever ready and valid. A target in melee is allowed. | Targeted regiment message (text resource `GMTXT` 2008). The click alone need not launch a shot. |
| Building or furniture | Retain that object as the target. Enter repeated building shooting. If in the front arc but beyond range, shoot toward it at 90% of maximum range. | Targeted building message (`GMTXT` 2007). |
| Shooter itself | Clear the fixed target and search for a target. Each ready search selects the nearest eligible enemy within missile range. | Searching message (`GMTXT` 2009); with Independent Archers, moving to search message (`GMTXT` 2017). |
| Unoccupied ground | Keep the clicked coordinates for one attempt. Check readiness, then front arc, then range; if all pass, order one volley. The point is not a lasting target. | On failure, reloading (`GMTXT` 2003), outside front arc (`GMTXT` 2002), or out of range (`GMTXT` 2001), according to the first failed check reached. No reload bar or counter is established. |
| Minimap point | Same object or ground interpretation after conversion to battlefield coordinates. | Same as corresponding row. |

`Ctrl` while issuing Fire on an eligible flying Archers class Gyrocopter selects a bomb drop at its own position. A grounded craft refuses with `GMTXT` 2020. For normal bows and longbows, holding Ctrl **at projectile launch** selects the alternate projectile drawing; damage, aim, range and flight time stay the same. It is not an ammunition or damage mode. Whether Ctrl changes any other ordinary graphic is unresolved. The Gyrocopter's Infantry class steam gun is a separate innate attack, not the bomb order.

The Independent toggle changes how Archers search and pursue shooting opportunities. A search order may advance toward a target, reselect a nearer target, and avoid a target with friends too close to the intended hit area. An ordinary selected unit target stays selected across volleys until invalidated or replaced by another order; Independent can instead enter a hunt of the current target or nearest available target. The exact friendly proximity check in hunt mode has an unresolved coordinate quirk, so implement a geometric check with a radius of `target footprint + max(blast radius, 24)` as an explicit engine choice. It does not make friendly or neutral units immune to an explicit Fire click or to impacts.

Automatic search excludes broken, hidden and leaving units, and looks for hostile units rather than buildings. Explicitly selected broken units can remain a shooting target while in range. A hidden unit cannot ordinarily be picked in the battlefield view. **Uncertain:** the complete predicate for an explicitly named hidden target from a script is not established. If a selected target disappears, the targeted loop must stop launching at its former position; searching or Independent may select another. If a target moves before the fire event, the shot aims at the target's current position at launch. Once launched, aim and scatter are fixed: it does not home and can miss or hit an intervening object.

| Shooter state | Trigger | Next state |
|---|---|---|
| Idle or moving | Accepted unit or building Fire click | Halt if moving; keep selected object; targeted repeated shooting. |
| Idle or moving | Accepted self click | Halt if moving; clear fixed object; search repeatedly. Independent Archers may advance while searching. |
| Idle or moving | Accepted ground click | Halt if moving; retain coordinates for a single attempt, then finish with no retained firing target. |
| Targeted, search or hunt | Reload complete, animation request complete, valid target in arc/range and valid line | Stamp reload; start shoot pose; launch only on its animation fire events. |
| Targeted | Target in range but outside arc, shooter mobile | Turn toward target; wait for halt; retry while target remains. |
| Targeted | Target lost, shooter broken, machine lost, or replaced order | Stop the current target loop; a search/hunt path may acquire another eligible target. |
| Projectile in flight | Target moves, dies or becomes hidden | Keep the already scattered destination and continue geometric collision checks. |

### Validation and refusal order

The persistent unit loop tests reload and then arc/range and crossbow obstruction before ordering another volley; the building loop tests arc/range before reload. Thus a unit target that is both reloading and out of arc waits for reload first; a building target can enter its long range fallback. These loops are normally silent. The ground one attempt path requests messages: readiness first, then arc before range. Readiness tests cooldown, then machine present for Artillery, then at least two crew; the otherwise available hold fire state is not set by shipped scripts. A crossbow line blocked by a nonenemy unit fails validity without a dedicated warning message. The unit remains targeted and may fire later when the line clears. Arc is strict `abs(wrapped bearing − facing) < 64` (±45°); range is strict `distance < maximum`. A ground point at the shooter's own position skips the arc rejection.

A targeted unit within range but outside arc turns toward it if mobile, then waits for its halt before a volley. The turn trigger is a bearing difference over 16/512 turn (11.25°); the shooting arc still uses 64/512. An anchored live war machine cannot turn or move, so an out of arc target remains unshot. Reload does not revoke events already posted by the current pose. Losing models during the pose can reduce the number of launches.

There is no general ballistic skill to hit roll. The only aim inaccuracy is scatter. No moved, long range, or cover to hit modifier is established. Scenery can increase scatter and physically intercept a shot.

## 2. Shared shooting and projectile lifecycle

The player order and scripted shooting both select a target or point and invoke the same readiness/volley path. A script may also order a shot at a map node, a 90% range shot, or fire at will. Ordinary Archers order action 7 for every model with a countdown initially equal to model count `N` and divisor 4. Each model reaches the pose's fire step on pose tick 2, 3, 4 or 5, selected by its random entry. Its arrival decrements the countdown; when the new value is divisible by 4 it posts one launch event from **that model's current position**. Therefore a complete volley makes `ceil(N/4)` projectiles, not one per archer. Artillery orders the machine/leader pose with divisor 1 and launches one projectile. Reload is stamped when the volley pose is ordered; a launch event later in that pose still runs if the cooldown is now active. See `script_animation_sound.md` §2 for queued poses and abandoned volleys.

Each ordinary missile needs: source unit and source model; weapon code and statistics read from its game data; launch point and height; target coordinates sampled at launch; scattered destination; elapsed and total flight ticks; trajectory rule; visual selection; radius, wound die, strengths, save and damage kind; and whether it has already hit. Source unit exclusion applies during flight but **not** at terminal impact. The active ordinary missile pool has 32 slots. If full, no additional ordinary projectile is launched; the exact visible failure behaviour is uncertain, so make the shot consume its already ordered volley event without adding a projectile.

For each axis, the destination offset is

`(random integer 0 .. 10−min(BS,10)) × independent random sign × spread × distance/max_range`.

For bows/crossbows, `spread = 8`, or 16 when scenery obstructs the straight aim line. For artillery, `spread = 8d` or `8d+8`, where `d` is the first misfire die (1–5 on a fired shot). The scenery test considers buildings, walls, trees and other solid objects between firer and aim point; a shooter inside an object's footprint is not blocked by it. It raises scatter but does not automatically cancel the shot. Randomness and integer rounding should be fixture controlled; the exact rounding at every intermediate product is **uncertain**.

The launch position is the posting archer's model position, or the machine/leader position for Artillery. The projectile's launch height is normally the local ground height; rock lobber and Doom Diver start 24 units above it. The selected target's height affects the desired endpoint, while a ground click uses ground level. **Uncertain:** the target height rule for every model family has not been reduced to a portable formula; use the picked object's geometric centre as an engine choice and keep that choice isolated.

Horizontal movement is linear from launch to scattered destination over the weapon's fixed flight ticks. Height interpolates between launch and aim height with an added rise and fall: bows rise by about 20 per early tick (peak about 180), crossbows by 5 (peak about 45), cannon and Hellblaster by 10 over their shorter flight, mortar and rock lobber by 30 over 27 ticks. Doom Diver rises by 10 over 18 ticks. An ordinary Gyrocopter bomb falls vertically over 9 ticks. The existing public report's “bows apex ≈180” is an approximate visual property, not a discrete height algorithm. **Engine choice:** use a symmetric triangular rise/fall with the stated step and a flat middle section for 18 tick bow flights. Keep trajectory coefficients data driven by weapon code so a later geometric refinement does not affect damage logic.

At each tick, advance position and height, then inspect intersected map objects and the terrain surface. Any ordinary missile hitting the first object at an intersecting height applies an **in flight** impact there and is removed. An ordinary arrow or bolt inside a unit footprint hits one random model. A blast projectile intersecting a unit footprint in flight hits **every** model at full strength; its blast margin is disabled for that flight hit. An intersected solid scenery object can stop it, with damage only if it is a damageable building/furniture target. If the projectile goes below the terrain surface it ends without a terminal blast. Otherwise, after the final flight tick, apply one **terminal** impact at its fixed scattered destination at ground height, with its positive blast radius; then remove it. At that stage every object in range is considered, including the firer. A moving target that leaves the area is not followed; another unit or scenery that enters the path can be struck.

## 3. Impact, damage and deaths

At impact, consider each object at horizontal distance `q` from the impact point. A unit is eligible only when projectile height overlaps its vertical extent; a flying unit must overlap between its raised base and top. If `q < unit footprint radius`, this is a direct hit: zero radius strikes one random model; positive radius strikes every current model. If not direct and `q < footprint radius + blast radius`, this is the margin: `n = max(1, trunc((footprint+radius−q) × unit size/(footprint+radius)))` random model picks **with replacement**, each at `trunc(S/2)` for exactly one wound. The direct hit uses the weapon's wound die. Each model rolls the existing S versus T wound rule, then an armour save when allowed, then takes wounds; a multi wound model can survive a single hit. Leaders use armour items. All ordinary missiles permit armour saves and are nonmagical. A regenerating model has the already documented missile immunity. A terminal blast can hurt friendly and neutral units, the firer, and units engaged in melee.

Buildings and furniture use their first owning model, building strength rather than model strength, no armour save, the same direct wound die, and one wound at half building strength on a blast margin. Bows and crossbows have no building strength and do not damage them. Other solid scenery can intercept a missile without taking unit damage. Direct and margin combat messages use `GMTXT` 2004/2005; an in flight collision is not required to show a terminal impact message. After any missile hit on a unit, test panic when its remaining size is at most a quarter of original size; this is a separate impact panic request in addition to any panic from deaths. Gyrocopter bombs omit that impact panic request. No ordinary missile has forced rout. The damage kind for ordinary missiles, including artillery and the bomb, is 2: a lethally wounded figure switches to its ordinary corpse after **one tick**, with random facing. A multi wound survivor remains alive; only the lethal hit selects the death kind.

Special shooters are separate from the ordinary missile table. Dragon breath (code 14) creates D6+3 magical, no save fire projectiles around its target, S8 and one wound; a hit forces rout and a kill uses fire death kind 1. Warpfire (15) creates D6 magical, no save S4 flames around its target, one wound, warpfire death kind 3; it does not use artillery misfire. A Gyrocopter steam gun (the Infantry class use of code 17) is a short range magical, no save S4 projectile that continues through units. An Archers class Gyrocopter can instead drop the ordinary blast bomb by Ctrl Fire while airborne. The Doom Diver is ordinary artillery, radius zero; no steering is established. Its terminal landing leaves a corpse decal with no game effect. Doomwheel lightning and Pestilent Breath are innate spell effects; their flight, scatter and damage are in `notes/spell_effects.md` §3.3 and §3.7 (each launch is an active effect, `spell_effects.md` §1).

Fire and warpfire death figures, where that family's death animation supports them, use `GENBATT` burn groups followed by a charred corpse. The groups and durations are already in `game_rules.md`'s “Death kinds” table and `engine_gaps/figure_animation.md`. The Warpfire Thrower's own death from a nonfire wound emits five flame puffs two ticks apart and a final radius 48, D6, S5 warpfire blast; its victims use kind 3. The Giant's death produces a radius 40, D6, S5 kind 2 blast. **Uncertain:** the precise tick of the final Warpfire Thrower blast. Apply it after the fifth puff as an engine choice.

## 4. Artillery lifecycle and reload

A live machine and at least two crew are required at readiness time. The artillery formation is anchored while the machine exists. A machine destroyed by combat or an explosive misfire clears the anchor; surviving crew become mobile infantry and cannot continue firing that machine. The loss also ends a pending machine shot if its animation has not posted the launch event. **Uncertain:** if the machine disappears after a launch event is queued but before it is serviced in the same tick, use the event queue's ordinary order.

Reload in ticks is `base = (10−min(I,10))×18`, reduced for bow codes by the table in `game_rules.md` §8, with a minimum of 18 for those bows. Artillery adds `36×(4−current crew size)` when fewer than four crew remain; readiness then also needs at least two. Use the crew Initiative, including for a cannon. Examples: bow with I2 → 101 ticks; crossbow I3 → 96; artillery I3 with four crew →126, with three →162, with two →198. **Uncertain/conflict in older public wording:** `game_rules.md` introduces 19 ticks per segment but its reload formula and examples use 18; implement the explicit tick counts, not a segment conversion.

At each ordinary artillery launch, roll a D6 before creating the projectile. Results 1–5 fire normally and also set the scatter multiplier `d` to that result. On 6 roll another D6. A second 2–6 loses the shot, shows `GMTXT` 2019, and leaves the machine intact. A second 1 destroys it, shows `GMTXT` 2018, gives each crew member an independent 50% chance of one wound, then tests surviving crew Leadership; failure routs them. In both misfires the volley has already stamped reload. The destroy result clears the anchor and removes firing eligibility. The ordinary Artillery shot, including the Doom Diver, uses this rule. The Gyrocopter bomb also makes the misfire roll; **uncertain:** whether its destructive result affects a distinct machine model in all Gyrocopter variants, so keep that consequence isolated in the bomb adapter.

## 5. Visual and audio resources

Use resources from the user's installation at runtime. `GMCUR.DLL` cursor group **100** is Fire (bow and arrow), **101** default (hand), **102** Attack (sword), **103** Magic (wand). These are installed resource mappings, not provisional labels. The Fire cursor appears when the Fire button arms an order and the ordinary cursor returns after resolution or cancellation. No established HUD reload meter or ammunition number exists; the ground attempt may display the reload refusal message.

The figure's shoot pose is action 7, with the family specific frames in `.FOL/.BOP/.PAL`; standard archer sets place shoot at frames 104–111, and the Warpfire Thrower uses its own shoot group. Use `animations.md`'s `group_start + phase×8 + direction` rule and the animation script's fire event step. Missile and spell effect visuals have resources in the battle's `SCENERY.PBX` furniture records, including `Arrows*` and `Explosion1..8`, and in `GENBATT`/`SPELLS` for figure effects; `sprite_names.md` records their names. **Established:** normal bow Ctrl selects a second projectile graphic; cannon/mortar/rock lobber/Doom Diver have distinct flight variants; Doom Diver adds a corpse decal. **Uncertain visual mapping:** exact scenery record for each weapon, pitch/orientation quantization, frame progression and explosion frame schedule are not established by a visual original game check. Use direction from the projectile velocity and advance the named effect frames once per battle tick as a documented engine choice. Keep visual ids in a resource mapping, separate from physics and damage.

`MISSILE.SFX` provides named effects for cannon, cannon explosion, rock lobber, archer, arrow, combined bow shot, Doom Diver and mortar; `SFX_Fire_ShootArrow` is the ordered archer plus arrow flight list. A weapon launch selects its corresponding named cue if the battle loaded the packet. `Battle2` and race packets also hold combat and death cues. **Uncertain:** exact per weapon playback timing and impact sound selection, especially when the battle does not load the missile packet; use the closest named loaded cue at the launch or impact event, and avoid a fabricated cue when absent. Burning and corpse graphics follow the existing death effect report; their frame to group mapping remains visual.
